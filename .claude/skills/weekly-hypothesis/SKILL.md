# 週次の仮説イシュー

計測は自動で回っていても、**数値から原因を考える工程**が止まると何も起きない（#505 は表を貼るだけで放置された）。
このスキルは、その工程を人との対話で毎週1回まわす。

## 原則

1. **毎週かならずイシューを1本作る。** 習慣を止めないことを優先する
2. **ただし、問題をでっち上げない。** 強い兆候が無い週は「確かめるための小さな調査」をイシューにする（例: 「〇〇ページの直帰率が高いのは、表示速度か内容か切り分ける」）
3. **1週間で終わる大きさにする。** PR 1本か、調査1回で閉じられること。大きいものは最初の一歩だけを切り出す
4. **対話で決める。** エージェントは事実と候補を出し、文脈（告知・イベント・障害・リリース）と選択は人が持つ
5. **事実・推測・判断を分けて書く**

## 手順

### 0. 前回までを振り返る（最初にやる）

```bash
gh issue list --label weekly-hypothesis --state all --limit 10 --json number,title,state,closedAt,url
```

- 先週のイシューが閉じていれば、その「完了の条件」の指標を今週のデータで確かめ、**仮説が当たったか**をイシューにコメントする
- 開いたままなら、理由をユーザーに聞く（大きすぎた・優先度が下がった・忘れていた）。答えを記録に残す
- `tasks/weekly-hypothesis.md`（gitignore 済みのローカル記録）を読み、過去に**却下した候補とその理由**を把握する。同じ理由で却下されるものは今週の候補にしない
- このファイル末尾の「よくある外れ」も読む

**月の最初の実行なら、ここで「月次の見直し」（後述）を先にやる。**

### 1. 計測結果を集める

比較の基本は **直近7日 vs その前の4週の平均**。破滅派は母数が小さいので、少ない数（目安: 週100セッション・100クリック未満）の増減は兆候として扱わない。

| 情報源 | 取り方 | 見るもの |
|---|---|---|
| Lighthouse CI | 下のコマンドで最新の実行の artifact から表を作る（表はログには出ない） | 「悪い」の境界を超えたページ、前回からの悪化 |
| Search Console | MCP `google-search-console`（サイト `sc-domain:hametuha.com`）。データは2〜3日遅れるので、期間を GA4 より3日前にずらす | クリック・表示回数・CTR・掲載順位の変化が大きいページとクエリ |
| GA4 | MCP `google-analytics-mcp`（`properties/338754670`） | 流入元別・端末別・国別のセッションとエンゲージメント率、主要イベント（`ad_impression` など）の日別の推移 |

```bash
# Lighthouse CI: 最新の実行の結果を表にする（<scratch> はスクラッチパッドの空ディレクトリ）
id=$(gh run list --workflow=lighthouse.yml --status completed --limit 1 --json databaseId --jq '.[0].databaseId')
gh run download "$id" -n lighthouse-reports -D <scratch>
for f in <scratch>/*.report.json; do cp "$f" "<scratch>/lhr-$(basename "$f" .report.json).json"; done
node .github/scripts/lighthouse-summary.mjs <scratch>
```

**GA4 の全体の数字はボットで大きく揺れる。** 2026-11 時点で、セッションの大半が中国・シンガポールの PC Chrome（流入元なし・エンゲージメント率が極端に低い）だった。
全体のセッション数・PV で比べず、**日本に絞った数字**か、エンゲージメント率と組み合わせて見る。
変化を見つけたら、国・流入元・ページで分解してから事実として出す（分解せずに「PV +40%」と出さない）。

MCP が使えないとき（`.mcp.json` が無い・認証切れ）は、その旨を伝えて、使える情報源だけで進める。

### 2. 事実を見せて、文脈を聞く

変化の大きいもの上位5件程度を**事実として**表で見せる（実数を出してよいのは対話の中だけ）。そのうえで聞く。

- この週に何があったか（告知・SNS・文学賞やイベントの締め切り・障害・リリース・季節要因）
- 気になっていることはあるか

この答えで説明がつく変化は、仮説の候補から外す。

### 3. 仮説の候補を出し、選んでもらう

候補を **2〜3件** 出し、`AskUserQuestion` で1つ選んでもらう。候補にはそれぞれ次を付ける。

- **証拠**: どの数値がどう動いたか
- **仮説**: 原因の推測。コードやデータで裏が取れているかを明記する（「裏付けあり」「推測」）
- **確かめ方**
- **外れの条件**: 何が出たらこの仮説は外れと言えるか。**書けない仮説は候補にしない**
- **大きさ**: 1週間で終わるか

候補のうち少なくとも1件は「推測」でも取り組める調査型にしておく（強い兆候が無い週でも1本作れるように）。
開いているイシューと重複する候補は出さない（`gh issue list --state open --search "<キーワード>"` で確かめる）。

### 4. イシューを書いて、確認してから作る

`references/issue-template.md` の形で下書きし、**本文をユーザーに見せて了承を得てから** `gh issue create` する。

- **公開リポジトリなので、GA4・Search Console の実数は書かない。** 前週比・割合で書く。実数が要るときはユーザーに確かめる
- **作品名・作者名に結びつくアクセス数、個人名を含む検索クエリは書かない**
- Lighthouse の数値は公開情報なので、そのまま書いてよい
- ラベルは `weekly-hypothesis` ＋ 内容に応じて `bug` / `enhancement` / `analysis`。`weekly-hypothesis` ラベルが無ければ作ってよいか聞いてから作る

### 5. 記録する

`tasks/weekly-hypothesis.md` に追記する（無ければ作る）。

```markdown
## 2026-11-24
- 作ったイシュー: #000 タイトル
- 選ばなかった候補: 〇〇（理由: ユーザーいわく文学賞の締め切りの影響）
- 先週の結果: #000 は仮説どおり／外れ（指標がどう動いたか）
- 振り返りのメモ: （進め方で引っかかったこと）
```

## 月次の見直し

月の最初の実行で、手順0のあとに行う。目的は**このスキル自体を良くすること**。

1. 過去1か月の `weekly-hypothesis` イシューと `tasks/weekly-hypothesis.md` から集計する
   - 作ったイシューの数、1週間以内に閉じた数、閉じられずに残った数
   - 仮説が当たった数・外れた数・確かめられなかった数
   - 選ばれなかった候補と、その理由の傾向
   - 実行しなかった週の数
2. 傾向から、このファイルの書き換え案を出す。例:
   - 同じ理由で外れる仮説が続く → 「よくある外れ」に足す
   - イシューが大きすぎて閉じない → 手順3の大きさの基準を厳しくする
   - 実行しなかった週が多い → 起動方法（定期実行への移行など）を相談する
3. **書き換えるかはユーザーが決める。** 了承を得たら、このファイルを直してコミットする（作業ブランチで）

## よくある外れ

月次の見直しで足していく。仮説を立てる前に必ず照らし合わせる。

- Lighthouse の LCP の飛び値は、シミュレーション（lantern）の見かけの数字のことがある。`observedLargestContentfulPaint` と比べる（#522）
- Cloudflare Polish はキャッシュに無い回に元画像を返すので、画像の重さは回によって大きく違う（#524）
- 指標が急に変わった日がリリース日と重なっても、運営側の手作業（広告設定など）が原因のことがある。リリースを疑う前に、その日に管理画面で何か変えたかを聞く（2026-11: 広告表示の半減は自動広告をやめたためだった可能性が高い）
- 流入元に見慣れないドメインがあり、エンゲージメント率が 100% 近い・トップページだけに来ている場合は、ゴーストスパム（GA の計測 ID を直接叩くもの）。サイトには来ていないので、サイト側の対策は不要
- 週の変化が「始まった日」は日別の推移で確かめる。週の合計だけでは、リリースや設定変更と結びつけられない
